## Large-Body Capacity Experiment

Ran the candidate's Linux/amd64 httputil test binary in a local isolated runtime
container: memory=1536 MiB, memory+swap=2048 MiB, CPU=1, network=none. It reused
an existing runtime image only; no application image was built or deployed.
Eight concurrent unknown-length bodies alternate 59/85 MiB; successful bodies
are retained until all reads settle. Release is idempotent and a subsequent
small request succeeds. Explicit opt-in: `SUB2API_RELEASE_CAPACITY=1`.

| Budget MiB | Accepted / rejected | Remaining reservations | cgroup peak bytes |
| --- | --- | --- | --- |
| 256 | 2 / 6 | 0 | 615211008 |
| 512 | 4 / 4 | 0 | 814444544 |
| 1024 | 8 / 0 | 0 | 1197527040 |

Post-GC live heap was under 180 KiB after each round. The cgroup peak is a
high-water mark across the same container, not a per-round RSS delta. This
isolates ingress allocation behavior; it is NOT full gateway/SSE/protocol
conversion/database/real-traffic capacity acceptance. The 1 GiB budget leaves
limited room for those components under the historical 1.5 GiB app limit.
No production configuration or container resource limit was changed.
