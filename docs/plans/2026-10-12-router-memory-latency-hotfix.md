# Router 内存与长等待的小范围修复计划

日期：2026-10-12。状态：第一批代码候选已实现；相关回归及单请求验证通过，两个 85 MiB 请求并发未通过容量门槛，因此未上线。用户本轮仅授权第一批，其他修复未实施。详见 [第一批实现与验证](../ops/2026-10-12-ops-snapshot-guard-validation.md)。

## 决策

第一批只修错误快照的大请求分配问题。验证并观察后，第二批再处理明确的上游过载重试。保留现有架构和协议转换，两个修复分别交付，避免同时改变内存、路由和超时而无法判断效果。

当前 Router 的 1.5 GiB 内存额度是故障缓解措施；暂时保留，不减回已再次失去响应的 1 GiB。计划不承诺仅靠快照修复就能容纳任意数量的大请求，也不把上游推理等待视为已经解决。

## 已有证据

详见 [本次故障记录](../ops/2026-10-12-router-latency-recovery.md)。

- 线上出现约 59–85 MiB 请求；1 GiB 内存及 512 MiB swap 耗尽时 Router health 停滞，入口返回 503。在线扩容后恢复，没有重启或换镜像。
- 本地合成 59 MiB 请求，错误快照单次累计分配约 177 MiB；OAuth 解码、转换、序列化单次累计分配约 379 MiB。累计分配不等于同时驻留内存，不能相加当作线上 RSS。
- 请求结束后内存回落到约 200 MiB，支持请求峰值及重试驻留的解释；没有线上 heap profile，尚未证明持续内存泄漏。
- 错误请求快照是我们 fork 恢复的定制路径。上游 [PR #2581](https://github.com/Wei-Shaw/sub2api/pull/2581) 已删除该处理；生产已包含上游部分大请求优化，单纯升级 v0.2.15 不会自动移除本地定制。
- 上游过载确实存在；反复重试可把失败请求延长到数分钟。首字延迟还包含上传、长上下文和上游推理，不能只用一个统一超时处理。

## 第一批：在解析前限制诊断快照的处理体积

### 改动范围

预计只修改一个生产代码文件 `backend/internal/service/ops_service.go`，补充已有 service、handler 测试。无需数据库迁移、前端改版或新增配置项。

在 `PrepareOpsRequestBodyForQueue` 入口按原始字节数判断，先于 JSON 解码、脱敏和重编码执行：

| 原始请求体积 | 诊断快照行为 |
|---|---|
| 空正文 | 保持现有行为 |
| 不超过 1 MiB | 保持现有脱敏和裁剪，入库上限仍为 256 KiB |
| 超过 1 MiB | 直接生成固定的小型 JSON 标记，不扫描、复制或解析正文 |

1 MiB 是诊断处理的输入阈值，选择它是为了保留现有约 512 KiB 快照测试及中等大小请求的诊断行为；它不改变业务请求大小限制。

超大正文的固定标记包含 `payload_truncated=true` 和 `snapshot_omitted_reason=request_body_too_large`；已有 `RequestBodyBytes` 记录准确原始体积，`RequestBodyTruncated=true`。模型、账号、错误码继续使用现有日志字段，不从大正文重新提取。请求头沿用现有白名单。

原始业务请求仍按现有规则校验、转发；不裁剪用户上下文或图片，不将正文前缀当快照。`sanitizeAndTrimJSONPayload` 的其他用途保持原样，防止影响错误响应正文处理。超大请求将失去完整正文诊断，这是本批明确的取舍。

### 必须通过的验证

1. 入口边界：阈值前、恰好阈值、阈值后；空正文、小型非法 JSON、小型敏感字段脱敏保持原行为。超大正文只产生固定标记和准确体积，不包含正文或凭据。
2. handler 到日志条目的连接：截断标记和体积正确，头白名单有效，异步日志条目不携带原始大正文。错误详情弹窗能显示现有截断提示。
3. 合成 59/85 MiB 分配对照：fixture 在计量前构建，单独测快照入口；目标为每次额外分配小于 1 MiB，且不随正文体积线性增长。分别报告累计分配和堆峰值，不混用口径。
4. 同版本隔离环境，以模拟上游过载验证一个、两个并发大请求及重复错误记录；观察 health、内存峰值、释放、日志和客户端终态。不得将真实用户正文重放到测试环境，也不向生产发送合成 85 MiB 压测请求。
5. 正常短文本、图片、工具调用的相关已有回归通过；实测成功请求以正常结束事件为准，不能只检查 HTTP 200。

第一批的局部验收是消除快照的额外全量处理。若隔离环境两个大请求仍让 health 超过 1 秒或触及容器限额，应停止推进发布，单独评估在途大请求预算；不能把局部分配改善宣称为容量问题已彻底解决。

## 发布与观察：保持一次只改一个因素

- 按现有 hotfix → release 候选 → 生产验证 → main 流程交付，不夹带上游升级。实际版本号和候选镜像在执行时确认。
- 部署前按 [部署入口](../engineering/deployment.md) 只读核对 Router 生产目标、当前镜像、配置挂载、资源额度和备份状态。没有现成的已验证自动替换脚本，也没有当前可直接使用的旧测试环境；不得套用历史部署命令。
- 本批保留 1.5 GiB 硬内存、总内存加 swap 2 GiB，以及现有 GC 配置。代码发布需受控替换 Router 容器；不与 GC 参数调整同时实施。
- 发布后完成正式域名的真实模型请求，记录客户端首个可见文本、总耗时和成功结束；与同模型、同推理档位、相近输入的基线比较。
- 连续观察 30–60 分钟，并覆盖至少一个真实大请求/错误峰值；没有覆盖时继续保留“峰值验证未完成”。观察限额命中计数增量、memory/I/O PSI、swap、health、503、错误比例与请求完成后释放。成功标准是入口持续可用、未新增限额命中，且没有引入请求语义或成功率回归；不能要求所有大请求内存都维持在 200 MiB。
- 出现入口 503、health 持续异常或新业务回归，回退兼容的原镜像并保留 1.5 GiB 额度与当前生产配置；不恢复旧数据库快照、不减回故障额度。原镜像本身存在快照风险，回退只撤销新增回归，不代表根因解决。

## 第二批：仅收敛明确的上游过载重试

启动条件：第一批验收后，普通请求仍有大量等待，并且证据指向 `server_is_overloaded` 的重复尝试，而非正常推理或上传耗时。若当前过载仍严重，可先在第一批验证期间准备此项的只读分析和测试样本，代码与发布仍分开。

- 只针对已明确识别的过载错误、且仍满足现有安全重试条件的请求。目标为同账号初次失败后最多再试一次，再进入已有可用账号切换逻辑。
- 保持现有账号可用性判断及已开始业务输出后的流式行为；不全局关闭账号、不改变工具结果处理，不对所有网络错误一起降重试。
- 先测量各次尝试耗时和用户端到端等待，再为普通请求确定总重试预算；高推理请求单独评估。不能用全局 30 秒一刀切，也不能用每次尝试重置的计时替代总预算。
- 用模拟过载 → 成功、持续过载、没有备用账号、已开始业务输出等样本验收；正常长上下文和高推理不能被新策略误伤。预期改善失败等待和大正文重发次数，不承诺使过载的远端模型变快。
- OAuth 路径不靠设置 `pool_mode_retry_count` 完成此修复；当前该设置不控制这条重试路径。实际修改位置须沿现有 handler 重试链确认。

## 暂缓项与升级条件

本次不安排 OAuth 全量重写、全局请求大小下调、新队列/调度器、数据库或 Redis 调整，也不为修本次问题整体合并上游。

若第一批后的隔离并发验证或真实峰值仍出现容量压力，再单独设计大请求在途字节预算，这是剩余 OAuth 全量解码成本的保护措施。Go 软内存目标可作为独立配置实验，但不能限制活跃请求所必需的内存；需要观察 GC、延迟及宿主机余量，不能作为容量保护的替代。

执行顺序：快照小修复 → 分配和隔离并发验证 → 受控发布与峰值观察 → 按证据决定过载重试修复或容量保护。每批单独记录结果、风险和回退，验收未通过就停在该批，不扩大为架构改造。
