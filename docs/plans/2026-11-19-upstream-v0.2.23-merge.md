| --- | --- | --- |

## 合并预演

已执行 `git merge-tree --write-tree --name-only main v0.2.23`：退出码 1 表示有冲突，虚拟结果树 `a789542a7682d56be934eac50169b638a95007e4`，没有改动任何工作区。只有 6 个文件冲突：

| 冲突文件 | 冲突原因 | 决策 |
| --- | --- | --- |
| backend/cmd/server/VERSION | 0.2.20 对 0.2.22 | 写 0.2.23 |
| backend/internal/handler/openai_gateway_handler.go | 我们加了 `setOpsRequestBodySnapshot(c, body)`（ops 快照保护），上游在同一位置加了 UTF-8 检查 | 两边都要：先做 UTF-8 检查返回 400，再记 ops 快照，然后继续原流程 |
| backend/internal/repository/group_usage_rollup_trigger_integration_test.go | 我们把上游 222/223 重编号为 229/230，上游新增 251 | 保留我们的 229/230，加上新编号 277（见下面数据库部分） |
| backend/internal/service/auth_service.go | 我们重排过这个文件（Studio 免 Router token 登录/注册、affiliate 等），冲突块很大；上游实际只改两处：`shouldApplyEmailFirstBindDefaults` 开头加 nil 检查，`RefreshTokenPair` 改用 `ConsumeRefreshToken` 原子消费 | 以我们的版本为底，只手工补上游这两处改动；`bindOAuthAffiliate` → `applyAffiliateSignup` 保持 |
| backend/internal/service/gateway_claude_oauth_body.go | 我们有 Opus 4.7 删除 temperature/top_p/top_k 的分支；上游改了 temperature 默认补 1 的条件（Fable/Mythos 5.2 不补，Sonnet/Haiku 5.5 只传 top_p 时不补） | 保留 Opus 4.7 分支；else 分支换成上游的新条件。补单测覆盖 Opus 4.7、Sonnet 5.5 只传 top_p、Fable 5.2 三种情况 |
| backend/internal/service/openai_responses_orphan_precheck_test.go | 我们上次把零分配测试放进子进程跑；上游做了同样的事 | 采用上游写法，删掉我们的重复版本 |

两边都改过、但 git 自动合并没报冲突的文件有 79 个，必须人工看：wire_gen.go / wire.go、config.go、ent/schema/group.go 和 9 个 ent 生成文件、go.mod / go.sum、embed_on.go、scheduler_cache.go（上游 +317 行）、gateway_service.go、openai_gateway_usage.go、user_group_rate_repo.go、migrations_runner.go、SettingsView.vue、PaymentView.vue、deploy/Dockerfile 等。"没有文本冲突"不等于"行为没变"。

上游动到我们关心的区域：payment provider 里的 alipay.go / easypay.go 和 payment_config_service.go、scheduler_snapshot_service.go、embed_on.go、deploy/Dockerfile。没有动 Studio auth、image_creation、wxpay、referral 的文件。执行后要对这些我们自有文件做逐字节比对。

## 数据库

main 有 328 个 SQL，最大编号 273。上游新增 5 个，统一往后编号，同步改测试和 runner 里的文件名引用：

| 上游文件 | 新编号 | 作用 |
| --- | --- | --- |
| 249_add_usage_logs_api_key_cost_index_notx.sql | 274_add_usage_logs_api_key_cost_index_notx.sql | usage_logs 上 CONCURRENTLY 建覆盖索引，不锁表，但表大时首次启动会慢 |
| 250_openai_cache_write_ttl.sql | 275_openai_cache_write_ttl.sql | usage_logs 加 30m/12h 缓存 token 列（默认 0），4 张定价表加 12h 价格列（默认 NULL） |

| 251_group_usage_rollup_nonblocking_build.sql | 277_group_usage_rollup_nonblocking_build.sql | 汇总状态表加列、替换失效触发函数；`lock_timeout=5s` |
| 252_channel_pricing_ultrafast_multiplier.sql | 278_channel_pricing_ultrafast_multiplier.sql | channel_model_pricing.ultrafast_multiplier，默认 NULL，带正数约束 |

要点：

- **runner 里写死了文件名**：上游在 migrations_runner.go 新增 `usageLogsAPIKeyCostIndexMigration = "249_..._notx.sql"`，用来在重跑前删掉失败的半成品索引。必须改成 274 的文件名，否则这个保护失效。同理检查 `group_force_openai_ultrafast_migration_test.go`、`usage_log_api_key_cost_index_test.go`、`group_usage_rollup_migration_test.go` 里的文件名。
- 已有 328 个 SQL 字节不变，不改旧 SQL、不改生产 checksum。
- 真实 PG18 升级测试：328 → 333，重复启动不重复执行；用户/余额/订单/套餐/配额不被改；新列默认值正确。保留历史升级测试的冻结文件集，新增 v0.2.20 → v0.2.23 一条，不是把旧断言里的数字改掉。
- 发布前（另授权）要只读查生产 usage_logs 行数和大小，估计 274 建索引时间；首次启动期间健康检查不能因为慢而把容器判死。
- Ent：按老规矩接受上游生成文件，手工合 `ent/schema/`，再 `go generate ./ent/...`；Wire 手工维护 wire_gen.go，保留 Studio / ImageCreation / Referral / MCP provider。生成两次零漂移。

## 执行步骤和停止点

1. 准备：确认 main 没变；装 Go 1.27.4、Node 24、pnpm 9；本地起 PG18 和 Redis（已有 postgres:18-alpine、redis:7-alpine 镜像）。从固定 main 建 `release/v0.2.23` worktree。
2. 合并：`git merge --no-ff v0.2.23`，按上表解决 6 处冲突；改 VERSION；迁移重编号 274–278 并改 runner 常量和测试引用；生成 Ent/Wire；逐个过 79 个双改文件。
3. 编译修复：先让 `go build ./...` 和 `go vet` 通过，再跑测试。修复只做最小改动，不为过测删除本地测试。
4. 验证：Go default/unit/integration 全量（真实 PG/Redis，不能用 skip 当通过）；认证、body 预算、调度快照、扣费的 race 测试；前端 lint、typecheck、全量 Vitest；embed 构建；`make build` 报 0.2.23；golangci-lint、govulncheck；升级矩阵 328→333；本地自有文件逐字节比对。
5. 重点回归（本地模拟上游）：
   - 同一用户高并发扣费：余额、订阅额度、用量记录只扣一次，不多不少；
   - 调度快照：冷却账号不被选中，大分组选号正常；
   - 流式首包前空闲超时换号只发生 1 次，不重复计费；
   - 缓存写入 5m/1h/30m/12h 计费：新旧价格对比，差异都能用发布说明解释；
   - refresh token 并发刷新：只有一个成功，其他返回失效，不会把正常用户踢下线。
6. 本地 code review：对固定 main 的累计改动、冲突处、计费/认证/调度交汇处做一次独立 review（交给 Codex 或独立 agent，不用我自己的结论去引导）。有阻断问题就修了重测。
7. 停止点：提交并推送 `release/v0.2.23` 到 origin，写 execution 记录（测试结果、review 结果、剩余风险），然后停下等用户确认。不登录服务器、不构建发布镜像、不部署、不合 main。
8. 发布（另授权）：只读预检生产（运行版本、512 MiB 环境变量、备份新鲜度、usage_logs 大小、磁盘/内存）；本机构建 linux/amd64 镜像；备份后切换 Router；验收正式域名、Studio 签名、真实模型调用、计费抽样；观察通过后再合 main。
