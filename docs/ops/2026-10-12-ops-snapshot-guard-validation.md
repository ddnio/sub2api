## 实现范围

生产代码仅修改 `backend/internal/service/ops_service.go`：在 `PrepareOpsRequestBodyForQueue` 完整 JSON 处理前检查原始体积。超过 1 MiB 返回固定 JSON 标记、原始字节数及截断标志；较小正文继续使用原有脱敏和 256 KiB 存储限制。

原始业务正文不修改，错误响应正文的处理函数、账号、路由、重试、GC、数据库及 Redis 配置保持原样。两个已有测试文件补充边界和异步日志队列验证。

代码提交：`d32154752f70e07c1ddd7a738a8e5ddf5e5514a4`。工作分支 `hotfix/ops-request-snapshot-guard-20261012`，候选分支 `release/v0.2.14-snapshot1`。与生产源码相比，原有 backend/frontend/Dockerfile/entrypoint 无差异后再加入本修复，未合并上游。

| 原始正文 | 旧快照入口每次累计分配 | 新入口每次累计分配 |

## 原生 Linux 并发验证：发布门槛失败

在 NAS 的原生 Linux x86_64 上使用临时、无外部网络、只读的测试容器；限额 1536 MiB、内存加 swap 总上限 2048 MiB、1 CPU。未部署完整生产栈，未连接生产数据库或真实上游，未重放用户内容。

临时 Go overlay 加载测试 harness，运行当前真实 OAuth `Forward` 与修复后的快照入口。使用预先构造的合成 inline-image 正文，模拟上游 503 过载；每条请求保留原有四次尝试，另用同一 HTTP server 检查 health。该测试覆盖服务转发和快照组件，完整入口鉴权、数据库与队列连接由相关回归补充，不能称为整套生产容量复现。

| 正文与并发 | 容器采样峰值 | health 最慢 | 限额命中增量 | 结果 |
|---|---:|---:|---:|---|
| 59 MiB × 1 | 566.0 MiB | 147.0 ms | 0 | 通过 |
| 85 MiB × 1 | 879.3 MiB | 153.6 ms | 0 | 通过 |
| 85 MiB × 2 | 1536.0 MiB | 1674.1 ms | 926 | 未通过 |

两个并发样本均完成预期的模拟失败终态，总计八次上游调用；但触及内存限额，health 超过计划的 1 秒门槛。释放请求、两次 GC 后 heap 约 3.95 MiB；这不等于已经观察到进程 RSS 同时完全回落。

此前 Mac Docker 的 x86 仿真单请求也出现 health 超时；其时序不能当原生生产性能。换到原生 x86 后，单请求门槛通过，两个并发仍失败。因此没有以仿真差异为理由忽略并发失败，也没有下调门槛或扩大内存来使测试通过。

结论：本批消除了快照路径随大正文产生的额外全量处理，但剩余 OAuth 解码、转换、序列化和重试驻留仍可产生容量压力。依照已批准计划，暂停候选发布；不扩大为重试、容量或协议改造。
